- 打开失败（权限、二进制零字节）用 `try/except` 兜底，返回 0 行并记录失败，可选打印警告，但不中断整个遍历。

```python
from pathlib import Path
import sys

def count_lines(file_path):
    """返回文件行数，读取失败返回0并可选报错"""
    try:
        with open(file_path, 'r', encoding='utf-8', errors='ignore') as f:
            return sum(1 for _ in f)
    except (OSError, UnicodeError):
        # 权限拒绝、二进制文件等静默跳过
        return 0

def main(root_dir):
    root = Path(root_dir)
    if not root.is_dir():
        print(f"错误: {root_dir} 不是目录", file=sys.stderr)
        sys.exit(1)

    results = []
    for fpath in root.rglob('*'):
        if not fpath.is_file():
            continue
        # 可选过滤：跳过隐藏文件或特定类型
        lines = count_lines(fpath)
        results.append((str(fpath), lines))

    # 降序排列
    results.sort(key=lambda x: x[1], reverse=True)

    for path, lines in results:
        print(f"{lines:>8} {path}")

if __name__ == "__main__":
    if len(sys.argv) != 2:
        print("用法: python linecount.py <目录>", file=sys.stderr)
        sys.exit(1)
    main(sys.argv[1])
```

**设计说明**  
- 参数从命令行取，符合你的环境习惯。  
- 行数右对齐 8 位输出，方便肉眼扫描。  
- 不统计目录、不处理符号链接指向的目录（`is_file()` 已过滤掉了链接到目录的路径，除非它是指向文件的符号链接，此时统计链接指向的文件行数——合理）。  
- 核心是 **“不出意外地跑通”** 和 **“出意外时别崩”**：编码忽略、权限跳过、二进制文件无声略过（返回 0 行）。如果你需要严格报错，可以把 `try` 块拆细、区分异常类型。

**1. 末尾空行和最后一行无换行**

Python 文件对象迭代是基于 `\n` 分割，但**会返回“最后一行”即使它没有换行符**。  
- 文件内容 `"a\nb\nc"`：`for _ in f` 产生 `"a\n"`, `"b\n"`, `"c"` → 3 行。  
- 文件内容 `"a\nb\nc\n"`：`"a\n"`, `"b\n"`, `"c\n"` → 3 行。  
- 文件内容 `"a\n\nb\n"`：`"a\n"`, `"\n"`, `"b\n"` → 3 行。  
所以**末尾的空行（即文件最后一个字符是 `\n`）不会被多数一行**。`sum(1 for _ in f)` 计算的实际是 **line count** 而非 **newline count**，与 `wc -l` 行为一致：`wc -l` 统计换行符个数，所以末尾空行会多数一行（`printf "a\nb\n" | wc -l` → 2，`printf "a\nb" | wc -l` → 1）。此处我用的方法等价于 `wc -l` 去掉末尾换行差异。如果你需要严格与 `wc -l` 一致，应当用 `sum(1 for ch in f if ch == '\n')`，然后再判断文件最后一个字符是否为 `\n` 决定是否 +1。但**题目要求“行数”而非“换行数”**，通常文本编辑器和版本控制系统按“行数”处理，所以我选择的是直觉版本。

如果你想要 `wc -l` 的语义，可以这样修复：
```python
def count_lines_wc(file_path):
    try:
        with open(file_path, 'r', encoding='utf-8', errors='ignore') as f:
            # 统计换行符个数
            return sum(1 for ch in f if ch == '\n')
    except (OSError, UnicodeError):
        return 0
```
但需要说明这会造成“最后一行有换行反而多算一行”的差异。

**4. 并行版本设计**

目标：分治统计 + 合并排序，避免 IPC 成为瓶颈。  
关键洞察：**文件读取是 IO 密集，但统计行数本身是 CPU 轻量**，所以 `ProcessPoolExecutor` 可以减少 GIL 影响，但主要收益来自并行 IO（前提是存储子系统支持并发读取，如 NVMe）。  
设计思路：
- 用 `ProcessPoolExecutor` 的 `map`，将任务按文件分块。每个 worker 接收一个文件路径列表，返回一个 `list[(path, lines)]`。
- 主进程用 `futures.as_completed` 收集结果，将所有小列表合并到一个大列表，最后一次性 `sort()`。文件总数通常不会大到内存装不下，排序耗时 O(n log n) 相比 IO 时间可忽略。这样避免了外部归并排序的复杂 IPC。
- 传输路径字符串成本低（短字节），远小于文件内容传输，所以 IPC 不是主要瓶颈。
- 负载均衡：为确保大文件不阻塞，可以用 `chunksize=1` 或精心划分文件列表，每块文件大小均衡（比如先快速 stat 获取大小，再按大小分桶），但简单情况先按路径数均匀切分即可。
- 极端大目录（百万文件）时，可能内存不够放所有结果，那时再考虑用堆合并或写入临时文件再归并，但我估计你环境中极少遇到。

代码骨架：
```python
from concurrent.futures import ProcessPoolExecutor
import os

def batch_count(file_list):
    res = []
    for fpath in file_list:
        lines = count_lines(fpath)  # 复用之前函数
        res.append((fpath, lines))
    return res

def parallel_count(root_dir, workers=os.cpu_count()):
    all_files = [str(p) for p in Path(root_dir).rglob('*') if p.is_file()]
    # 按 workers 数目均分
    chunk_size = max(1, len(all_files) // workers)
    file_chunks = [all_files[i:i+chunk_size] for i in range(0, len(all_files), chunk_size)]

    results = []
    with ProcessPoolExecutor(max_workers=workers) as executor:
        for batch_res in executor.map(batch_count, file_chunks):
            results.extend(batch_res)

    results.sort(key=lambda x: x[1], reverse=True)
    return results
```

排序是集中式的，但在百万级文件中，`sort` 性能依然很好。  
这就是一个“不引入分布式复杂度的本地并行”方案，适合你的语境。

**纯标准库可以做编码探测吗？**

能做，但仅限于有限情况，而且误判率高。标准库没有通用编码检测器，能用的手段大致是：

1. **BOM 检测**  
   用 `codecs.BOM_UTF8`、`codecs.BOM_UTF16_BE` 等，读文件头几个字节比对。但这只对带 BOM 的文件有效，绝大多数 UTF-8 文件不带 BOM。

2. **尝试常用编码列表**  
   依次用 `'utf-8'`、`'latin-1'`、`'cp1252'`、系统默认编码打开文件，第一个不解码抛异常的就算“命中”。问题是 `latin-1` 从不抛异常（它覆盖全部 256 个字节），所以永远是备胎但可能结果乱码。这种策略能基本区分 UTF-8 纯净与否（因为 UTF-8 有严格的无效字节序列），但对单字节编码之间毫无分辨力。

3. **启发式字节检查**  
   可以读文件前几 KB，检查是否符合 UTF-8 编码规则（RFC 3629）。如果不符合，就假定是单字节编码，再用 `locale.getpreferredencoding()` 或者 `'cp1252'`。这依然是猜测。

4. **基于频率的猜码**  
   可以编写一个非常简陋的“记分器”：按字节分布尝试 UTF-8、中文 GBK、日文 Shift-JIS 等高频特征。但这已经是在模仿 `chardet`，而你自己写的版本必然更简陋、更难维护，且仍需维护一堆语言模型。这已经相当于重新发明轮子。

我的原则不是“绝不引入依赖”，而是“*除非必要，不增加外部负担*”。这里的“必要”包含维护负担、准确性需求、环境复杂度。

破例边界条件：
- **准确性要求很高**：编码猜错不仅影响行数（如多字节字符被错误分割导致换行符识别异常），还会使后续处理失效。如果统计只用于粗略估计，可以容忍 `errors='replace'`；如果你会把结果喂给其他程序做进一步处理，编码错误就不可接受。
- **文件来源混杂**：目录里混合了 UTF-8、ISO-8859-1、GBK、Shift-JIS 等，且没有统一约定。此时手工启发式基本无效，引入 `chardet` 是唯一务实解。
- **维护成本反转**：自己写简陋启发式会产生持续维护需求（不断有人报“这个文件编码你又猜错了”）。而 `chardet` 是成熟库，帮你吸收了这些 bug，长期看更省力。
- **环境许可**：`chardet` 是纯 Python 库，没有任何系统级依赖，可以在受限环境中运行（比如离线部署、容器）。如果你的环境真的绝对无法 pip install（例如某些安全管制下的 air-gap 系统），那就必须退回标准库试探 + `errors='replace'` + 给用户明确警告。

**所以我的结论：**
- 在单机开发、目录少、来源可控（我自己生成的）—— 标准库试探就够。  
- 在多用户、多来源、严肃统计的脚本里 —— 引入 `chardet` 是值得的，因为它显著降低长尾问题，而带来的依赖成本极低。  

零依赖是起点，不是信仰。当“维护简陋猜测器”的开销超过“引入 `chardet` 的负担”时，我会毫不犹豫破例，并在脚本开头写明为什么破例，让下一个维护者理解这不是随意之举。
